## 3. 核心技术要求

### 3.1 权限分级机制（赛题优先级：高）

等级由纯函数策略引擎 `server/policy/engine.ts` 判定：从工具声明的基础等级出发，规则**只能升级或拒绝**；用户确认时在执行锁内重新判级；扣款事务内再查一次日累计。详见 [SECURITY.md §3](SECURITY.md#3-权限分级)、算法见 [ALGORITHMS.md §1](ALGORITHMS.md#1-风险分级策略引擎)。

**转账的黄 / 红界限与赛题完全一致**：北京时间自然日、跨本人全部账户的转出累计（含本笔）**≤ 1000 元为黄色，> 1000 元为红色**；恰好 1000 元仍为黄色。早期版本另有"夜间单笔超过 500 元""7 天内新增收款人"两条升红规则，已于 2026-10-13（`0d547d4`）移除，此后转账分级只看日累计。

| 赛题等级 | 赛题示例 | 文财实现 | 状态 |
|---|---|---|---|
| 🟢 绿色 · 自动执行 | 余额、交易记录、账单分析、理财收益查询 | 所有只读工具（`kind: 'read'`）为绿色，直接执行；测试保证没有写工具是绿色 | ✅ |
| 🟡 黄色 · 用户确认 | 小额转账（日累计 ≤ 1000 元） | 转账类基础等级黄色，展示服务端生成的确认单 | ✅ |
| | 订阅查询 / 取消 | 查询为绿色；取消为黄色 | ✅ |
| | 虚拟卡申请 | `apply_card` 黄色 | ✅ |
| 🔴 红色 · 强验证 | 大额转账（日累计 > 1000 元） | 规则 `transfer-daily-total`：北京时间自然日、跨本人全部账户累计（含本笔）超过 1000 元升红 | ✅ |
| | 密码修改 | 按卡修改密码在独立安全页面先完成强验证；账户级改密工具为红色 | ✅ |
| | 卡片挂失 / 解挂 | `report_card_lost`、`unlock_card` 基础等级红色；`commit_card_change` 的挂失 / 解锁 / 调额由规则升红 | ✅ |
| | 理财产品申购 | `commit_purchase`、`commit_fund_order` 红色 | ✅ |
| | 多因子认证（人脸、短信、U 盾等） | 付款卡交易密码 + 短信或模拟指纹 / 人脸；单笔超过 3000 元或收款账户可疑时，第二步只接受指纹 / 人脸 | ⚠️ 指纹 / 人脸为明确标注的模拟按钮；没有 U 盾 |

**在赛题分级之上的补充，答辩时主动说明**（都不改变 1000 元的黄 / 红界限）：

1. **黄色转账也需要一次付款凭证。** 赛题的黄色只要求"确认"；文财在已注册用户动用银行卡或资金账户时，确认后还要求交易密码、短信、模拟指纹或人脸**任选其一**。理由是卡密码属于支付凭证，确认按钮只能证明"看过"，不能证明"本人同意动用这张卡"。等级本身仍是黄色。
2. **红色内部的验证组合**：单笔超过 3000 元（此时日累计必然已超过 1000 元，本来就是红色）或收款账户被标记可疑时，第二步只接受模拟指纹 / 人脸，不接受短信。这只改变红色的验证方式，不新增等级。
3. **按风险事实升级或拒绝**：收款账户被 AI 标记可疑升红、被人工确认高危直接拒绝；10 分钟内 5 笔转账熔断；商城单笔超过 3000 元或开启自动续费升红；账户锁定期间拒绝非只读操作。

**渠道能力上限**：Web/H5 可到红色；飞书到黄色，超出时跳转 H5；MCP 只读。

### 3.2 安全机制（赛题优先级：高）

| 赛题要求 | 文财实现 | 状态 | 详见 |
|---|---|---|---|
| **幻觉防护**：不得编造交易结果或账户信息 | 余额、确认单、回执、理财建议走服务端数据渲染的固定组件；模型正文先缓存、核验后再发送：金额与卡尾号必须能在服务端证据中找到出处，流水的日期 / 金额 / 尾号必须来自同一笔，没有成功回执的"已完成"说法被替换；生成式界面禁止数字字面量 | ⚠️ 数字核验暂不识别"万"和中文数字 | SECURITY §7、ALGORITHMS §4 |
| **注入防御**：防止通过特殊 Prompt 绕过权限控制 | 三层：① 输入审核（NFKC 规范化 + 规则，可并行 Qwen3Guard），拦截的消息不进入模型；② 工具输出中他人可控的文本过审核并加隔离标记；③ 结构性限制：工具参数没有 userId、系统中没有可被模型调用的确认工具、等级由代码决定 | ⚠️ 只审核最后一条用户消息 | SECURITY §6、ALGORITHMS §5 |
| **操作审计**：完整的决策链路与执行日志 | 用户输入、审核判定、工具调用、策略判定（含命中规则与当时事实）、确认、执行、补偿、注入清洗、输出核验、熔断、后台命令全部写入哈希链审计；后台"安全内核"页可追踪单次请求的完整决策链 | ⚠️ 哈希链未加密钥，只能发现直接篡改 | SECURITY §10、§16 |
| **异常熔断**：连续失败或可疑行为触发安全锁定 | 强验证或卡密码连续失败 5 次锁定账户 30 分钟，锁定期间所有非只读操作被拒绝；10 分钟内 5 笔转账触发熔断 | ⚠️ 反复注入尝试尚不会触发锁定 | SECURITY §4.7 |
| **沙箱环境**：生成的代码在受限、可监控的隔离环境运行 | 账单分析代码在 QuickJS（WASM）中运行：无文件系统、网络、`require`、`process`，1 秒超时、32MB 内存，输入冻结、输出只能是 JSON；后台可现场运行死循环、越权、内存炸弹样本 | ✅ | SECURITY §11 |

### 3.3 意图理解与任务规划

| 赛题要求 | 文财实现 | 状态 |
|---|---|---|
| 模糊表达、省略上下文、隐含意图 | 模型工具循环（最多 8 步）；缺失条件用即时生成的问卷补齐，真实对象（卡、收款人）用选择组件；收款人、银行卡按名称 / 备注 / 尾号消歧，多候选必须让用户选 | ✅ |
| 复杂任务拆解为子任务 DAG | `plan_task` 提交 1–12 个节点的 DAG：校验节点、工具白名单、依赖存在、`$ref` 只引用直接依赖、无环后拓扑执行 | ✅ |
| 执行中断 | 对话停止按钮把中止信号传到执行器，计划停在两个节点之间并保存为"已暂停"；任务中心可暂停、恢复、取消 | ✅ |
| 回退 | 失败或取消时逆序执行已完成写操作的补偿动作；缺少补偿或补偿失败时进入"失败"并转人工，不谎报回滚成功 | ✅ |
| 人工接管 | `handoff` 节点转人工；任务中心记录人工处理结果后继续，人工备注不能替代银行回执；后台可人工复核风险标记 | ✅ |

算法见 [ALGORITHMS.md §3](ALGORITHMS.md#3-任务-dag-执行与补偿)。

## 4. 演示边界（如实表述）

- 指纹 / 人脸为**模拟按钮**，界面明确标注，不采集生物特征；验证触发条件与"密码 + 生物验证"组合由代码强制执行。
- 短信：配置 `SMS_DELIVERY_URL` 即接入真实通道，尚未与服务商验收；演示环境验证码只打印在服务端日志。
- 商户、外部银行、授信审批、基金销售均为模拟；基金数据为公开接口的最新公布净值，不是实时行情。
- 飞书、Passkey 实机、MCP OAuth 尚未用真实环境验收。
- 对外表述统一按 [SECURITY.md §20](SECURITY.md#20-对外表述口径)：不说"零幻觉""防住所有注入"。
